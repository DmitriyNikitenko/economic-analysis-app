# Контракт данных прототипа

Документ описывает формат данных между расчётом графа и фронтом. Данные пишутся по этой схеме, фронт читает их по ней же. Менять поля можно только вместе, с правкой этого файла.


## 1. Общие правила

- Координаты: WGS84, порядок `[долгота, широта]` (как в GeoJSON, не как в Яндекс.Картах).
- Идентификаторы: строки вида `s_000123`, уникальные во всём наборе.
- Кодировка файлов: UTF-8. Числа в JSON с точкой, без разделителей разрядов.

## 2. Домены

| Код | Название | Статус |
|---|---|---|
| `money` | Деньги | используется |
| `labor` | Труд | используется |
| `goods` | Товары и услуги | заведён, **пока отключён** |

Домен `goods` присутствует в схеме и в конфиге, чтобы позже включить его без изменения структуры. Сейчас для него не определено, как считать ёмкость, поэтому `enabled: false`: граф по нему не строится, фронт не показывает переключатель.

### Роли узлов

Роль задаётся относительно домена. Один и тот же населённый пункт может быть спросом в одном домене и предложением в другом.

| Домен | Спрос (`demand`) | Предложение (`supply`) |
|---|---|---|
| `money` | населённый пункт (потребность в финансовых услугах) | банк, отделение |
| `labor` | работодатель (потребность в работниках) | населённый пункт (рабочая сила) |
| `goods` | населённый пункт (потребление) | магазин, объект услуг |

### Ёмкость по доменам

Ёмкость (`capacity`) — число, по которому считается вес ребра. Единица зависит от типа узла и домена.

| Домен | Узел | Что такое ёмкость | Единица |
|---|---|---|---|
| `money` | населённый пункт | население | человек |
| `money` | банк | условная мощность отделения, количество банкоматов или объем выданных кредитов | усл. ед. |
| `labor` | населённый пункт | трудоспособное население | человек |
| `labor` | работодатель | число вакансий | вакансий |
| `goods` | — | не определена **[открыто]** | — |

Для `money` пока нет согласованной прокси-величины для банка (число сотрудников, число точек обслуживания, кредитный лимит).

## 3. Таблицы DuckDB

### `subjects`

Один экономический субъект. Населённый пункт участвует в нескольких доменах, поэтому для него запись одна, а ёмкость по доменам лежит в `capacities`.

| Поле | Тип | Описание |
|---|---|---|
| `id` | VARCHAR, PK | идентификатор |
| `name` | VARCHAR | название |
| `kind` | VARCHAR | `settlement`, `bank`, `employer`, позже `shop` |
| `lon` | DOUBLE | долгота |
| `lat` | DOUBLE | широта |
| `address` | VARCHAR, NULL | адрес; опционален, нужен для геометрии по адресам |
| `district_id` | VARCHAR, FK | район из `districts` |

### `capacities`

Ёмкость и роль субъекта в конкретном домене.

| Поле | Тип | Описание |
|---|---|---|
| `subject_id` | VARCHAR, FK | субъект |
| `domain` | VARCHAR | `money`, `labor` (позже `goods`) |
| `role` | VARCHAR | `supply` или `demand` |
| `capacity` | DOUBLE | ёмкость, > 0 |

Первичный ключ: (`subject_id`, `domain`).

### `edges`

Результат расчёта, module edges. Ребро всегда идёт от стороны спроса к стороне предложения внутри одного домена.

| Поле | Тип | Описание |
|---|---|---|
| `id` | VARCHAR, PK | идентификатор |
| `domain` | VARCHAR | домен |
| `from_id` | VARCHAR, FK | субъект со стороны спроса |
| `to_id` | VARCHAR, FK | субъект со стороны предложения |
| `distance_km` | DOUBLE | расстояние между субъектами |
| `weight` | DOUBLE | вес узла, доля спроса узла from_id, достающаяся to_id (модель Хаффа), от 0 до 1 |

### `districts`

| Поле | Тип | Описание |
|---|---|---|
| `id` | VARCHAR, PK | идентификатор |
| `name` | VARCHAR | название района |
| `geom` | GEOMETRY | полигон границы |

### `metrics`

Результат расчёта, module metrics. Одна строка на пару (район, домен), плюс строки по региону.

| Поле | Тип | Описание |
|---|---|---|
| `scope` | VARCHAR | `district` или `region` |
| `district_id` | VARCHAR, NULL | район; для `region` пусто |
| `domain` | VARCHAR | домен или `all` |
| `node_count` | INTEGER | число узлов в расчёте |
| `edge_count` | INTEGER | число рёбер |
| `avg_degree` | DOUBLE | средняя степень вершины |
| `low_data` | BOOLEAN | `true`, если узлов меньше порога из конфига |

Средняя степень считается как сумма степеней узлов района, делённая на число этих узлов. Ребро учитывается в степени обоих концов.

## 4. Файлы для фронта

Экспорт кладёт файлы в `public/data/`. Фронт читает их через `fetch`, отдельного API нет.

### `subjects.geojson`

`FeatureCollection` из точек.

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": { "type": "Point", "coordinates": [30.3141, 59.9386] },
      "properties": {
        "id": "s_000123",
        "name": "Работодатель 7",
        "kind": "employer",
        "district_id": "d_02",
        "address": null,
        "domains": {
          "labor": { "role": "demand", "capacity": 84 }
        }
      }
    }
  ]
}
```

Поле `domains` содержит только те домены, в которых субъект участвует. Для населённого пункта их два: `money` и `labor`.

### `edges.geojson`

`FeatureCollection` из линий.

```json
{
  "type": "Feature",
  "geometry": {
    "type": "LineString",
    "coordinates": [[30.31, 59.93], [30.40, 59.98]]
  },
  "properties": {
    "id": "e_004512",
    "domain": "labor",
    "from_id": "s_000040",
    "to_id": "s_000123",
    "distance_km": 8.4,
    "weight": 0.37
  }
}
```

### `districts.geojson`

`FeatureCollection` из полигонов с полями `id`, `name`. Метрики сюда не дублируются, фронт соединяет их с `metrics.json` по `id`.

## 5. Конфиг `config/region.yaml`

```yaml
region:
  name: "Тестовый регион"
  crs: "EPSG:4326"

low_data_threshold: 5        # меньше узлов в районе — метрика помечается как ненадёжная

domains:
  money:
    enabled: true
    radius_km: 12            # R: ребро строится, только если расстояние не больше R
    beta: 2.0                # показатель затухания расстояния в весе
  labor:
    enabled: true
    radius_km: 15
    beta: 2.0
  goods:
    enabled: false           # заведён, пока не используется: не определена ёмкость
    radius_km: 8.5
    beta: 2.0
```

Значения `radius_km` и `beta` предварительные.

## 6. Вес ребра

Рабочая версия, гравитационная модель с обрезкой по радиусу:


```
weight(i, j) = S_j · d_ij^(−beta) / Σ_k ( S_k · d_ik^(−beta) ),   k пробегает объекты с d_ik <= radius_km
```

- `S_j` — ёмкость объекта `j` (`capacity` стороны предложения);
- `d_ij` — расстояние `distance_km`;
- `beta` и `radius_km` берутся из конфига для данного домена;
- ребро строится, только если `d_ij <= radius_km`; сумма идёт по тем же объектам;
- для каждого узла со стороны спроса веса исходящих рёбер в сумме дают 1;
- ёмкость самого узла `i` в вес не входит; абсолютный поток при необходимости считается как `capacity_i · weight(i, j)` и в схему не записывается.

Расстояние `d_ij` ограничивается снизу (например, 0,1 км), чтобы не делить на ноль, если узлы совпали по координатам.

Вес зависит от других объектов в радиусе, поэтому при добавлении или удалении объекта веса всех рёбер его узлов-спроса нужно пересчитывать.

## 7. Проверки целостности

Экспорт должен падать с ошибкой, если нарушено любое из условий:
1. Все `id` уникальны, все внешние ключи указывают на существующие записи.
2. `capacity > 0` и `0 < weight <= 1`.
2а. Для каждого узла-спроса и домена сумма `weight` его исходящих рёбер равна 1 с точностью до 1e-9; если рёбер нет, узел имеет степень 0.
3. Ребро соединяет узлы одного домена, `from_id` в роли `demand`, `to_id` в роли `supply`.
4. Узлы лежат внутри полигона своего района.
5. Домены с `enabled: false` не встречаются ни в одном экспортированном файле.
